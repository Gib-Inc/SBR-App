# SBR Operations App — Audit Feedback Report

**Date:** 2026-06-12 · **Reviewer:** Senior Engineering · **Scope:** sales integrity, aggregation/timezone, ad-spend integrity, AI hallucination, inventory/WAC, scheduler resilience, drift coverage, new FinOps code. All findings below were independently reproduced against the live DB (`txfhonbjxoetgvqqmoum`) before inclusion.

---

## 1. Executive Summary

The deterministic compute core of this app is genuinely well-built — WAC math, drift classification, forecast bias-correction, and the directive guardrails are defensively coded and pass 285 tests. The defects all live at the **I/O and identity boundaries** the tests don't cover, and several are firing in production right now. The single biggest risk is a **broken order-identity model**: the same physical Shopify order is being stored twice (once relabeled `AMAZON`, once `SHOPIFY`), and this one root cause cascades into double-counted revenue (**$27,132.60 live**), double-decremented inventory, inflated daily snapshots, and corrupted forecast/ROAS inputs. Stacked on top of that, ad-spend is inflated ~6.5x by summing overlapping rolling-window snapshots, which collapses blended ROAS below the 3x pause floor and produces **false September-Rule triggers** — and the Morning Trap SMS briefing is reporting Google as a "$0 sales / TOTAL CONVERSION TRACKING FAILURE" daily when the real issue is an unmapped attribution field.

**Is it trustworthy for an executive handoff right now? No.** Revenue, ROAS, and inventory numbers surfaced to decision-makers and to the AI agents are currently wrong in known, quantified ways, and the system-integrity scheduler that should catch this is itself mislabeled as permanently "failed." Three critical fixes (order identity, ad-spend overlap collapse, Morning Trap ROAS gate) plus the snapshot/inventory backfills must land before any number from this app is presented to Stacy, Christopher, or fed unattended into the agent stack.

## 2. Critical & High Issues

### CRITICAL

**C1 — Same physical order cloned across channels ($27,132.60 double-counted, live)**
*Location:* `server/services/shopify-client.ts:466-468` (`classifyChannel` + `externalOrderId=String(order.id)`) vs `server/routes.ts:7214` (SHOPIFY-scoped dedup); `sales_orders`.
*Why it matters:* 62 confirmed Shopify orders exist as both an `AMAZON` and a `SHOPIFY` row (124 rows), inflating revenue by exactly $27,132.60; all 1085 non-null AMAZON external ids are 13-digit Shopify-style, proving these are relabeled Shopify orders. Newest clone created 2026-06-11 — still happening.
*Fix:* Force canonical identity `(SHOPIFY, shopify_order_id)` for every order fetched from the Shopify API; store marketplace attribution (Amazon/Codisto) as a **separate column**, never as `channel`. Route all ingestion through one idempotent upsert on that key. Backfill-merge the 62 AMAZON clones into their SHOPIFY twins (preserving `order_name` + payload), then re-run `daily_sales` aggregation.

**C2 — Insert paths disagree on dedup key (channel-scoped vs channel-agnostic) — the active clone generator**
*Location:* `server/services/shopify-reconciliation-scheduler.ts:183` & `server/routes.ts:7414,8383` (`getSalesOrderByExternalIdOnly`, channel-agnostic) vs `server/routes.ts:7214,8592` & `server/shopify/webhook-handlers.ts:214` (`getSalesOrdersByExternalId(channel,…)`, channel-scoped).
*Why it matters:* The reconciliation scheduler looks up by external id alone and can relabel a row to `AMAZON`; the Shopify backfill checks only `('SHOPIFY', id)`, doesn't see that row, and inserts a clone. `createSalesOrder`'s 23505 net never fires because the channel differs. This will keep cloning every reconciliation+backfill cycle.
*Fix:* One canonical identity routed through a single idempotent upsert. Eliminate channel-agnostic lookups **or** make them universal — do not mix. Add a regression test that ingests one order via webhook, reconciliation, and backfill and asserts exactly one row.

**C3 — Cross-channel duplicate orders double-decrement `availableForSaleQty`**
*Location:* `server/routes.ts:8592` (Amazon dedup, channel-scoped) vs `7414` (Shopify dedup, channel-agnostic); `SALES_ORDER_CREATED` decrement at `inventory-movement.ts:230-234`, fired from `routes.ts:8809`.
*Why it matters:* Same root cause as C1/C2 hitting stock. Order `6557838508171` has two rows (identical customer, `#15728`, $292.04, same Shopify `source_url`); audit-log shows 8 dup orders fired `SALES_ORDER_CREATED` on both rows, each 1-unit sale recorded as `-2`. Inventory on affected SKUs is understated.
*Fix:* Make the Amazon dedup channel-agnostic — replace `getSalesOrdersByExternalId(orderData.channel, externalOrderId)` at `routes.ts:8592` with `getSalesOrderByExternalIdOnly(externalOrderId)` and update the existing row's channel in place instead of inserting. Add a UNIQUE index on `external_order_id` alone (`WHERE external_order_id IS NOT NULL`). Backfill: delete the 62 spurious AMAZON rows + lines, restore `availableForSaleQty` by the over-decremented amount per SKU.

**C4 — `getUnifiedPerformance` sums overlapping rolling-30d Windsor snapshots → ad spend inflated ~6.5x**
*Location:* `server/services/unified-performance-service.ts:320-331` (`+=` with no dedup) + `138-174` (`mergeAdSpendByPlatform`, Windsor wins when spend>0); `storage.ts:7698-7712` (overlap predicate).
*Why it matters:* For window 2026-05-14..06-13 the overlap query pulls 7 active GOOGLE rolling snapshots summing **$70,993.90** vs the correct latest-window $10,867.80 (AMAZON $27,156.50 vs $4,174.36; META $16,155.80 vs ~$2,651). Total bug spend $114,306.20 vs correct ~$17,693.90. On $204,688 revenue, blended ROAS reads **1.79x vs true ~11.6x** — below the 3x pause floor, so `generateDirective` emits PAUSE/HOLD and **trips the September Rule on platforms actually clearing target.** The high-ROAS implausibility gate (>20x) does not catch this deflated case.
*Fix:* Collapse each platform's active snapshots to the single one with the latest `period_end` before summing (port `morning-trap-service.ts:343-344`, which already does this), **or** make the Windsor sync supersede by period OVERLAP like the manual-Meta path (`routes.ts:24793-24799`). Backfill-supersede the 6 stale GOOGLE + 6 stale AMAZON rolling rows. Apply the same single-window collapse to the META uploaded bucket.

**C5 — Morning Trap reports Google "Sales: $0 | ROAS: 0:1" and escalates it daily as a "TOTAL CONVERSION TRACKING FAILURE"**
*Location:* `server/services/morning-trap-service.ts:319-357` (`googleAdsFromSnapshots`), `463-509` (`buildDataPayload`), `24-89` (system prompt); `morning_trap_runs`.
*Why it matters:* All 14 GOOGLE `marketing_spend_snapshots` rows have NULL revenue against $124,172 spend, so the code computes ROAS=0 and the prompt amplifies it into a false alarm. The 6/10, 6/11, 6/12 runs each persisted "GOOGLE ADS … Sales: $0 | ROAS: 0:1 TOTAL CONVERSION TRACKING FAILURE / 7,672 clicks … Zero conversions" — while real revenue ($233,360 net over 35 fully-populated days) sits in `daily_sales_snapshots`, never wired in. This is false, decision-driving output sent daily via SMS, and the Morning Trap has none of the data-quality gates the directive engine has (`isAttributionBroken`, `applyDataQualityGate`).
*Fix:* Gate the line before emitting — when snapshot revenue is null/0 with spend>0, emit "Sales: not attributed in feed" + a data-quality note, never "$0 / ROAS 0:1". Better, wire real attributed revenue (`daily_sales_snapshots` / `unified-performance-service`) into a blended ROAS. Add a prompt rule: $0 platform sales with non-zero spend is a missing conversion field, report as a data gap, never compute ROAS from it.

**C6 — Cross-channel twins evade the new channel-aware dedup AND the integrity sweep**
*Location:* `server/services/daily-sales-scheduler.ts:25-53` (`orderIdentityKey`/`dedupeOrdersByIdentity`); `server/services/system-integrity-service.ts:160-208,249-274` (dup sweep + `resolveSalesDuplicates`).
*Why it matters:* This is the same $27K twin set viewed from the defense layer — and the defenses miss it. `orderIdentityKey` namespaces by channel, so `SHOPIFY|#15534` and `AMAZON|6532373708939` survive as distinct. The integrity dup query and `resolveSalesDuplicates` both `GROUP/PARTITION BY channel`, so twins land in separate partitions; the live sweep returns 0 dup groups. Snapshot inflation = 18.2% of May25–Jun11 revenue, and no single day hits the 4x `salesMagnitudeAnomaly` trigger, so it never alerts.
*Fix:* (Prevention) Add a dup-sweep query that groups by `external_order_id` **alone** when the id is Shopify-format (`^[0-9]{10,}$`), independent of channel; fix the ingestion mislabel at root (C1). (Remediation) Remove the 62 AMAZON twins and re-derive affected `daily_sales_snapshots` so the forecast loop and anomaly median stop learning from inflated revenue.

### HIGH

**H1 — `report-context-builder.buildSalesReport` anchors today/week/month on UTC, not Mountain Time**
*Location:* `server/services/report-context-builder.ts:109-130`; consumed by `inventory-recommendation-batch.ts:546`; snapshots written in MT by `daily-sales-scheduler.ts:16-18`.
*Why it matters:* Every evening MT, UTC has rolled to tomorrow's date, so the "today" snapshot lookup returns $0 (real MT-today was 19 orders/$7,286.70) and the 7-day window misses a full day — verified understatement **$26,692.40 (32.7%)**. This wrong sales context feeds the AI inventory LLM. Intermittent by hour (correct during the 10 AM / 3 PM batch windows, diverges after ~6 PM MT), which makes it easy to miss.
*Fix:* Compute `todayStr/weekAgoStr/monthAgoStr/tomorrowStr` in `America/Denver` — reuse the scheduler's `getMountainDateString` and format each boundary with `toLocaleDateString('en-CA',{timeZone:'America/Denver'})` so lookup keys match how snapshots are written. Add a test pinning a fixed evening-MT `asOfDate`.

**H2 — Prompt injection: raw scraped supplier-page HTML feeds the price-extraction LLM, and the result auto-writes item cost + PO line totals**
*Location:* `server/services/llm.ts:1290-1320` (prompt assembly); `server/services/inventory-recommendation-batch.ts:874-917` (`createAutoDraftPO`).
*Why it matters:* `.substring(0,15000)` of untrusted page text is pasted straight into the prompt with no delimiter, no data/instruction separation, and `productName`/`sku` are interpolated unescaped. When confidence is high/medium the returned number sets `unitCost`, persists as `costSource:'AUTO_SCRAPED'`, and becomes `lineTotal = quantity * unitCost` → PO subtotal — fully automated, no human confirmation, no sanity bounds. This is the only audited path where untrusted external free-text reaches an LLM that writes financial data.
*Fix:* Wrap scraped content in an explicit fenced/XML data block with a system instruction that text inside is data, never instructions, and only a numeric price visibly shown as the product's price may be returned. Add sanity bounds (reject values far off prior cost or below a floor) and require human confirmation for any `AUTO_SCRAPED` change beyond a set percentage. Same isolation for `productName`/`sku`.

**H3 — Drift resolver treats SHIPPED orders as "open unshipped" because `qty_shipped` is never populated**
*Location:* `server/services/inventory-drift-resolver.ts:79-92` (`openUnshippedBySku`), `:84` (status exclusion list missing SHIPPED).
*Why it matters:* Line 84 excludes only FULFILLED/CANCELLED/DELIVERED/REFUNDED/PENDING_REFUND, and `qty_shipped` is `0` on every line in the DB (1020 SHIPPED units / 0 shipped). So all shipped-but-not-delivered units count as open, inflating `openUnshipped` and pushing AFS corrections too low — e.g. `#1202-REP-M2` correction `-98`. The ledger shows 2 rows already AUTO-CORRECTED off this broken premise.
*Fix:* Fast — add SHIPPED to the excluded-status set at `:84`; don't rely on `qty_ordered - qty_shipped` while `qty_shipped` is unpopulated. Durable — populate `qty_shipped` on SHIPPED/DELIVERED transitions. Dedupe the cross-channel AMAZON rows first (C1/C3), since they double-count open units for affected SKUs.

**H4 — `createSalesOrder` idempotency recovery looks up by `external_order_id` only (no channel, unordered LIMIT 1) — can overwrite the wrong channel's order**
*Location:* `server/storage.ts:6806` (recovery) + `6756-6761` (`getSalesOrderByExternalIdOnly`); index `server/startup-migrations.ts:44-48`.
*Why it matters:* On a 23505 the recovery calls a channel-blind `select().where(eq(externalOrderId)).limit(1)` with no `ORDER BY`, but the unique index is `(channel, external_order_id)`. With 62 shared external ids and mixed physical order (50 AMAZON-first, 12 SHOPIFY-first), a future Shopify re-import can silently overwrite the AMAZON row's financial fields in 50/62 cases. Latent — requires a future re-import that trips 23505 — but it's silent financial-record corruption.
*Fix:* Add `getSalesOrderByChannelAndExternalId(channel, externalOrderId)` using `eq(channel) AND eq(externalOrderId)` and call it from the 23505 handler. Pair with the C1 root-cause fix.

**H5 — System-integrity scheduler reports healthy DRIFT detection as a "failed" run**
*Location:* `server/services/system-integrity-scheduler.ts:24` (DRIFT→failed mapping); `server/services/scheduler-run-recorder.ts:38,75-117`.
*Why it matters:* The recorder sets `lastSuccessAt` only for success/partial/skipped; a DRIFT outcome is mapped to "failed," which writes a `SCHEDULER_CRASH` log, increments the consecutive-failure counter (now at 23), and leaves `last_success_at` permanently NULL. This is the **only** scheduler showing failed (14/15 are green). It actively masks a genuine future crash and hides drift state from the Health dashboard. *Caveat (verified):* ops-alert delivery is currently a no-op — no Slack/SendGrid configured — so no bogus alert has actually been **delivered**; the original "fires 24 bogus alerts" overstated it (23 failed runs, each attempting an undelivered alert).
*Fix:* Record the sweep as success/partial whenever it **completes** regardless of DRIFT, so `lastSuccessAt` advances and the counter resets; reserve "failed" for the catch block (thrown exception). Surface DRIFT via its own channel (it already persists to `app_settings.system_integrity_latest` and `data_reconciliation_log`; let `integration_health.error_message` carry the anomaly summary on a successful run). Reset `scheduler_consecutive_failures:system-integrity` to 0. Fix this before alerting is wired up, or the first real crash will be indistinguishable from steady-state drift.

## 3. Drift-Detection Coverage Gaps — "Are we catching any drift?"

**Short answer: partially, and the most expensive live drift (the $27K cross-channel twins) is slipping through every existing guard.** The sweep's dedup query, `resolveSalesDuplicates`, the partial unique index, and `dedupeOrdersByIdentity` are all channel-partitioned, so cross-channel twins are invisible to them. Below are the checks worth adding, each scoped and verified. Numbers reflect live state — most are structurally real but currently low-occurrence, so treat them as **preventive tripwires**, not active fires (except the first, which is firing).

**Gap A — Cross-channel Shopify-format duplicates (FIRING NOW — closes C6)**
Catches the twins the channel-partitioned sweep cannot see.
```sql
SELECT external_order_id, COUNT(*) AS rows, COUNT(DISTINCT channel) AS channels,
       SUM(total_amount) AS double_counted
FROM sales_orders
WHERE external_order_id ~ '^[0-9]{10,}$'        -- Shopify-format id only
  AND external_order_id IS NOT NULL
GROUP BY external_order_id
HAVING COUNT(DISTINCT channel) > 1;
```
*Threshold:* DRIFT if any group returned (≥1). *Severity:* **critical** (it's the live $27K inflation).

**Gap B — NULL-canonical-key rows escaping the index and the sweep**
The partial unique index and the sweep's dup query both require a non-null key; ~2161 rows (mostly Feb–Mar `is_historical` import) have NULL `external_order_id` AND `order_name`. Latent re-import risk of an ~$870K block.
```sql
SELECT COUNT(*) AS null_key_rows
FROM sales_orders
WHERE external_order_id IS NULL AND order_name IS NULL
  AND is_historical = false;          -- scope to live rows; historical is a known seed block
```
*Threshold:* WARN if >0; DRIFT if >5 non-historical. *Severity:* **low** (16 live rows; scope to non-historical — do **not** present as a "~49% blind spot," the 49% is almost all historical seed data).

**Gap C — Negative / zero-stock-but-selling inventory**
Schema has zero CHECK constraints on `items`, so negatives are permitted; sweep never checks. Currently clean (0 negatives).
```sql
SELECT
  COUNT(*) FILTER (WHERE available_for_sale_qty < 0) AS afs_neg,
  COUNT(*) FILTER (WHERE hildale_qty < 0)            AS hildale_neg,
  COUNT(*) FILTER (WHERE current_stock < 0)          AS comp_neg,
  COUNT(*) FILTER (WHERE available_for_sale_qty = 0
                   AND product_type = 'finished')     AS zero_but_selling
FROM items;
```
*Threshold:* DRIFT if any `*_neg > 0`; WARN if `zero_but_selling > 0`. *Severity:* **low** (preventive — zero live occurrences). A DB-level `CHECK (current_stock >= 0 …)` is a stronger, cheaper guard than a periodic sweep for the negative case.

**Gap D — Orphaned `sales_order_lines`**
No FK from `sales_order_lines.sales_order_id` to `sales_orders.id`; `resolveSalesDuplicates` deletes children and parents in two un-transactioned statements, so a partial failure can orphan lines. Currently clean (0 orphans).
```sql
SELECT COUNT(*) AS orphan_lines
FROM sales_order_lines l
WHERE NOT EXISTS (
  SELECT 1 FROM sales_orders o WHERE o.id = l.sales_order_id
);
```
*Threshold:* WARN if >0, DRIFT if ≥5. *Severity:* **low**. Better fix is structural: add an `ON DELETE CASCADE` FK and wrap the two deletes in `resolveSalesDuplicates` in one transaction so orphans cannot arise.

**Gap E — DATA_GAPPED snapshots silently summed into authoritative spend**
`getMarketingSpendSnapshotsInRange` filters only `superseded=false` + non-null period — no status filter — so a `DATA_GAPPED` AMAZON snapshot ($3,081.32) is summed with equal weight and never surfaced into `view.dataGaps`.
```sql
SELECT platform, period_start, period_end, status, spend
FROM marketing_spend_snapshots
WHERE superseded = false
  AND status = 'DATA_GAPPED'
  AND period_start <= :window_end AND period_end >= :window_start;
```
*Threshold:* WARN if any in-window; surface to `view.dataGaps`. *Severity:* **low** (compounds C4; exclude these from the sum or downgrade them once C4's single-latest-window collapse lands).

**Gap F — Forecast accuracy (MAPE) degradation — DEFER**
Only `daily_net_revenue` has actuals (3 points, MAPE 189.9%). Real flag, but 3 points is too few to threshold on. *Recommendation:* defer the sweep stream until ≥14 actualized points per metric. Separately worth a one-off look at why `daily_net_revenue` is at ~190% on its first 3 actuals (likely `correction_factor_used` mis-tuned). *Severity:* **low/defer.**

## 5. What's Solid

Credit where it's due — the core is real engineering, not scaffolding.

- **The deterministic FinOps compute layer is genuinely well-built and tested.** `weightedAverageCost` clamps every input (`Math.max(0, x||0)`), short-circuits zero on-hand, and guards divide-by-zero; `biasCorrectionFactor` clamps to `[1-clamp, 1+clamp]` with dampening; `classifyDrift` computes `targetAfs`/`correction` with correct signs; `salesMagnitudeAnomaly` floors low-volume baselines. **285 tests across 28 files pass.** The defects sit at the I/O boundaries these tests don't cover — the math itself is sound.
- **The directive engine already has the data-quality discipline the Morning Trap lacks.** `isAttributionBroken`, `IMPLAUSIBLE_BLENDED_ROAS=20`, and `applyDataQualityGate` (downgrade to HOLD on gapped feeds) are exactly the right patterns — the fix for C5 is to port them, not invent them.
- **The fix patterns for the hardest bugs already exist in-repo.** `morning-trap-service.ts:343-344` does the correct single-latest-window selection (the C4 fix), and `routes.ts:24793-24799` does correct overlap-supersede for manual Meta. The Meta path provably has no overlapping active snapshots — that mechanism works.
- **Daily-sales aggregation has no order-total fanout.** `getSkuSalesVelocity` and the marketing-analytics v2 SQL sum order-level totals without line-join fanout and correctly filter on `order_date`; `GROUP BY (channel, external_order_id) HAVING count>1` returns 0 dup groups — the within-channel index holds.
- **The Daily Briefing path is honest.** `briefing-service` and `report-context-builder` have zero LLM calls — numbers are computed from fully-populated storage data. The $0-alarmism is isolated to `morning-trap-service`, not here.
- **The scheduler fleet is resilient and re-run safe.** Each scheduler registers as an independent `import().then().catch()` block so one init failure can't block others; `recordSchedulerRun` wraps every write in try/catch; idempotency guards (`isRunning`, `ON CONFLICT (target_date)`) exist where it counts. 14/15 schedulers are green — only system-integrity is mislabeled (H5).
- **Exact-period and manual-Meta overlap-supersede both work correctly** — verified zero exact-period duplicates and zero overlapping active META snapshots in live data.
